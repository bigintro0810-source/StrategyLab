# 形状判定版 上昇ボックス(可変タッチ方式) 仕様書 v2

対象関数(予定): `ascending_box_shape`(既存実装を全面的に置き換える)

**注記: これは現行実装(`docs/pattern_spec_channel_patterns_shape.md`、4点固定・
共通コア方式)を置き換える新設計の仕様書。ユーザー判断(2026-08-15)で
「上昇ボックス以下5家系(ボックス/トライアングル/ウェッジ/ペナント/フラッグ)
すべてを作り直す」ことになったため、まず上昇ボックスをこの新方式の
リファレンス実装として仕様化する。下降ボックス以降4家系は、この仕様が
確定・実装・検証された後に同じ方式へ展開する。**

現行の4点固定共通コア(`_shape_state_core_channel`)とは前提から異なる
(タッチ回数が可変・全採用点の平均で水準を判定)ため、共通コアは流用せず
新設する。

---

## 1. 全体の考え方

現行実装は「点1〜点4の4点(山2・谷2)だけで完結」する設計だったが、この
v2は「上限タッチ2回以上・下限タッチ2回以上を最低条件に、条件を満たす限り
何回でもタッチを追加していく」可変タッチ方式に変更する。ボックスの水準は
个々の点ではなく、**採用された山/谷全体の平均**で決める。

---

## 2. 探索起点・事前条件

- 起点(山1)は確定ピボット高値。ピボット判定は既存のダブル/トリプル/H&Sと
  同じ非対称ピボット(`pivot_left_bars`/`pivot_right_bars`、既定**3/3**
  - 旧仕様案の「5本」から、既存パターンの現行初期値に合わせて修正)。
- 事前上昇の必須化は**なし**(ペナント/フラッグだけが旗竿を必須にする、
  という現行の使い分けをそのまま維持し、ボックスには適用しない)。

---

## 3. 構成点とピボット確認の使い分け

必須の最小構成は山2つ・谷2つ(山1・谷1・山2・谷2)。

| 点 | 確認方法 | 理由 |
|---|---|---|
| 山1 | 両側確認(`pivot_left_bars`+`pivot_right_bars`) | 起点。急がず確定させる |
| 谷1 | 両側確認 | 最小構成の一部、まだブレイクは起こり得ない |
| 山2 | 両側確認 | 最小構成の一部(これで山2つ・谷1つ) |
| 谷2以降 | **左側のみ確認**(`pivot_left_bars`) | 谷2が確定した時点で最小構成(山2・谷2)が揃い、以降いつブレイクが
起きてもおかしくない。トリプル/H&Sの「最後の1点だけ左本数のみ」と
同じ考え方を、点数が可変な分「最小構成が揃って以降のすべての点」に
拡張したもの |
| 山3以降 | 左側のみ確認 | 同上(谷2以降と同じ扱い) |

同方向のタッチ同士(山→次の山、谷→次の谷)は最低`min_touch_gap_bars`
(既定5)本離れていることを要求し、近接した複数のピボットを別々のタッチと
して過剰にカウントしない。

---

## 4. 水準許容誤差(採用条件)

2026-08-15訂正: 当初「採用された全ての山/谷の**平均**」を基準にする設計
だったが、「どの点を取り消すか」の判断が一意に決まらない問題があった
(§4.1参照)。**山最高値・谷最安値(平均ではなく極値)を基準にする**方式に
変更し、この問題自体を解消した。

```
ボックス高さ = 山最高値 - 谷最安値
許容誤差 = ボックス高さ × level_tolerance_mult(既定0.25)
```

新しい山候補が出現するたびに:

- **候補 > 現在の山最高値**(新しい山最高値を更新する場合): 候補を新しい
  山最高値として採用し、ボックス高さ・許容誤差を再計算する。既存の採用済み
  山のうち、`[新山最高値 - 許容誤差, 新山最高値]`の範囲に収まらなくなった
  ものを**全て**取り消す(複数・0個どちらもありうる、機械的に一意に決まる
  - 「どれを選ぶか」という判断は不要)。
- **候補 ≤ 現在の山最高値**: 候補が`[山最高値 - 許容誤差, 山最高値]`の
  範囲に収まっていれば採用(既存の山には手を付けない)。収まっていなければ
  候補を採用しない。

谷も同じ考え方(向きが逆、`谷最安値`を基準に`[谷最安値, 谷最安値+許容誤差]`
の範囲で判定)。

取り消しの結果、山・谷どちらかが2点未満になってしまう場合は、そのボックス
候補自体を無効(Invalidated)にする(最小構成を維持できないため)。

### 4.1 具体例

山1=110.00・山2=110.20が採用済み(山最高値=110.20、許容誤差=0.25と仮定)の
状態で、山3候補=110.35が出現した場合:

1. 110.35 > 110.20 なので新しい山最高値は110.35
2. 新しい範囲は`[110.35-0.25, 110.35] = [110.10, 110.35]`
3. 山1(110.00)はこの範囲に入らない → 取り消し
4. 山2(110.20)はこの範囲に入る → 維持
5. 結果: 採用済みは`{山2=110.20, 山3=110.35}`

## 5. 逸脱判定(範囲外への逸脱)

ボックス形成中、価格が新しい高値/安値を更新する**たびに**(確定ピボットで
なくても、ヒゲ単位で)、その新しい極値を候補として§4の判定式を再チェックする。

- 満たせば(取り消し処理を経て条件を満たす形にできれば)ボックス形成を継続。
- 満たさない場合(§4.1の取り消しをしても2点未満になってしまう等)、その
  ボックス候補は無効(Invalidated)。
- ただし、上抜け方向への新高値が§6の正式ブレイク条件(終値ベース)を
  同時に満たす場合は、逸脱ではなく**正式ブレイク(Confirmed)**として扱う
  (逸脱判定より正式ブレイクの判定を優先する)。

新しい高値/安値を更新しない(レンジ内で収まっている)バーはこの判定の対象外
- 新しい高値/安値を更新しないバーはそもそも§4の集合を変えないため、判定
しても意味がない(既存の採用済み集合がすでに条件を満たしている以上、
その範囲内のバーは自動的に条件内)。

### 5.1 谷1が見つかる前(2026-08-17、不具合修正)

実装当初、この逸脱判定は「箱の高さ」(山最高値-谷最安値)が既に存在する前提
(谷1が見つかった後)でしか動いておらず、**谷1を探している最中**(山1はある
が谷はまだ無い段階)に山1を大きく超える新高値が出ても、完全にノーチェック
のまま素通りしてしまう不具合があった(実データ検証で発覚 - 山1から883本後に
Confirmedしたパターンで、谷1が見つかる前に山1を1.1円以上上回る新高値が
出ていたのに、無視されたまま処理が続いていた)。

修正: 谷1を探している間も、山1を更新する新しい確定ピボット高値(両側確認)
が出現するたびに、山1自体をその新高値に置き換える(箱の高さがまだ無いため
「取り消し」ではなく単純な置き換え - 置き換え後は`max_box_bars`のタイムアウト
起点も新しい山1に更新される)。谷側の探索はこの新しい山1を基準に継続する。

## 6. 上方向ブレイク(Confirmed)

```
ブレイク上限ライン = 採用された山の最高値(水平線)
ブレイク余白 = ボックス高さ × breakout_buffer_mult(既定0.05)
```

`breakout_type`パラメータ(既定`close`、`close`/`wick`から選択)に応じて:
- `close`: 終値 > ブレイク上限ライン + ブレイク余白 でConfirmed
- `wick`: 高値 > ブレイク上限ライン + ブレイク余白 でConfirmed

ヒゲのみの突破(`close`指定時)ではConfirmedにしない(§5の逸脱判定に回る)。

---

## 7. 使用しないチェック(現行実装からの差分)

- カウフマン効率比・トレンドラインからの直線乖離 → **使用しない**
- 孤立度チェック(`pivot_spike_excess_atr_max`相当) → **使用しない**
- 事前上昇(旗竿)の必須化 → **使用しない**(ペナント/フラッグのみの概念として残す)

## 8. 最大本数(タイムアウト)

山1を1本目として、`max_box_bars`(既定**250**)本を超えてもConfirmed/
Invalidatedのどちらにも至らない場合は、そこで打ち切り(Invalidated扱い)。

## 8.5. 谷の深さ(ATR倍率) - 2026-08-16追加

ダブルトップ/ボトムと同じ考え方の谷深さフィルター。谷(opp)候補の採否判定に
以下を追加する:

```
depth = (山側極値 ext_box) - (谷候補の価格)   # 上昇ボックスの場合。下降は符号反転
depth_min = ATR(14) × min_valley_depth_atr_mult
depth_max = ATR(14) × max_valley_depth_atr_mult (0以下なら無制限)
採用条件: depth_min <= depth <= depth_max
```

ダブルトップ/ボトムは「直前・直後の山2点の平均」を基準にするが、この
可変タッチ方式では谷候補を評価する時点でまだ「直後の山」が見つかって
いないため、代わりにその時点の`ext_box`(山側の現在の採用済み極値、
この時点で必ず1点以上ある)を基準にする簡略化。「レジスタンスからどれだけ
押し込んだか」という趣旨は保ったまま、以降タッチが増えて`ext_box`が
更新されても、既に採用済みの谷の採否には遡って影響しない(採用時点の
`ext_box`で一度だけ判定)。

この判定は谷側(opp)の採用経路すべて(1つ目の谷、新極値としての採用、
既存レンジ内としての採用)に一律で適用する。不採用の候補は単にスキップ
され、探索は次の候補へ継続する(採否判定自体が探索の分岐先を変えるため、
フィルターを有効にした場合と無効にした場合で最終的な検出件数が単純な
包含関係にならない点は、ネック許容誤差など他パラメータの実データ検証
[docs/pattern_spec_head_and_shoulders_shape.md参照]で確認済みの一般的な
性質と同じ)。

## 9. パラメータ一覧(既定値)

| パラメータ | 既定値 | 意味 |
|---|---|---|
| `pivot_left_bars` | 3 | ピボット左本数(山1・谷1・山2の両側確認、谷2以降の左側確認に共通使用) |
| `pivot_right_bars` | 3 | ピボット右本数(山1・谷1・山2の両側確認にのみ使用) |
| `min_touch_gap_bars` | 5 | 同方向タッチ同士(山→山、谷→谷)の最低間隔 |
| `level_tolerance_mult` | 0.15(2026-08-17、0.25から変更) | 山/谷の採用条件(ボックス高さに対する倍率) |
| `min_valley_depth_atr_mult` | 1.0 | 谷の深さ下限(ATR倍率、§8.5) |
| `max_valley_depth_atr_mult` | 0.0(無制限) | 谷の深さ上限(ATR倍率、§8.5) |
| `breakout_buffer_mult` | 0.05 | ブレイク判定余白(ボックス高さに対する倍率) |
| `breakout_type` | `close` | ブレイク判定基準(`close`/`wick`) |
| `max_box_bars` | 500(2026-08-17、250から変更) | 山1からの最大本数(タイムアウト) |

## 10. 共通管理仕様

Candidate → Confirmed → Invalidated の3状態モデル、先読み防止
(未確定の右側ピボットを使わない)は既存パターンと同じ。

- **Candidate**: 最小構成(山1・谷1・山2・谷2)が揃った時点(谷2は左側確認
  のみで即座に確定するため、山2確定時点と谷2発見時点の遅い方)。
- **Confirmed**: §6の正式ブレイク条件を満たした時点。
- **Invalidated**: §5の逸脱判定、§8のタイムアウト、または最小構成を
  維持できなくなった時点。

---

## 11. 実装時の検証手順

1. 合成データ(山2つ・谷2つがほぼ同水準の教科書的ボックス)でCandidate/
   Confirmedが出ることを確認。
2. 3つ目・4つ目のタッチを追加した合成データで、§4.1の取り消しロジックが
   意図通り動くことを確認(古い点が取り消されるか、外れた点が取り消されるか)。
3. 逸脱(ヒゲが範囲外に出る)を含む合成データでInvalidatedになることを確認。
4. 実データ(USDJPY 15分足)で検出件数・実行速度を確認。既存実装(4点固定・
   共通コア版)との検出件数の違いも比較する。
