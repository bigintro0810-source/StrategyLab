## 0. 設計の経緯

2026-08-19、旧実装(`_channel_indicator`方式、4点固定・カウフマン効率比/
トレンドライン乖離などトリプル/H&S由来の質フィルター多数)を廃止し、
`ascending_triangle_shape` v2(下値支持線=常に引き直し可能な回帰直線)を
ベースに全面書き換えた。

**第1版(常に引き直し可能・両側独立)**: 当初は上値抵抗線も下値支持線と
同じ「常に引き直し可能」な方式にしたが、両側を完全に独立した引き直し
方式にすると、最小構成が揃った瞬間に2本の直線を延長するとどこかで
既に交差している、という問題が実データ検証で見つかった。

**第2版(段階固定方式)**: これを受けて、ユーザー提案により両側とも
「段階固定」方式へ再設計した - 最初の2点はそのまま結んで直線にし、
3点目のピボットが出現したら回帰直線を1回だけ引いて以降は固定する、
という方式(交差チェック§6・急さチェック§6.1を最小構成成立の瞬間に
1回だけ追加することで交差0件・非収束を大幅に削減した)。

**第3版(複数組み合わせ探索方式、現行)**: 2026-08-19、ユーザーから
「1つの起点に対して複数の組み合わせを探索する三角保ち合いと同じ方式に
してほしい。『3点目で1回だけ固定、以降は引き直さない』の本来の意図は
『同一の2点を使う回帰直線は複数引かない』であって、『同一の1点(起点)を
使う回帰直線は複数見つけて一つのパターンとして認識する』のは問題ない」
という指摘を受け、三角保ち合いv2の回帰側と同じ「起点固定+既存プールの
中間点+新しい候補、という組み合わせを古い方から順に試し、条件をすべて
満たす最初の組み合わせを採用する」方式に再設計した。段階固定方式で
1回きりだった交差チェック(§6)・急さチェック(§6.1)は、`_wedge_pool_
refit_side`の中に組み込み、**引き直しが起きるたびに毎回**やり直す形に
変更した(両側を独立に何度も引き直せる設計に戻すため、段階固定方式に
変えた元々の理由[交差]がそのまま再発しないよう、確認を都度行う)。

実データ(USDJPY 15分足)で検証したところ、段階固定方式(524件/165件)
から複数組み合わせ探索方式(1301件/557件)へConfirmed件数が大きく増えた
(1回の候補失敗で探索全体が打ち切られていたケースの多くが、別の組み
合わせで生き残るようになったため)。交差違反・非収束違反はいずれも
0件を維持している。

**表示の交互性のバグ2件(2026-08-19、同日中に発見・修正)**: 複数組み
合わせ探索方式に変えた直後、ユーザーから「構成点5個のうち4点目と5点目
どちらも安値になっている」という報告があり、実データで調査したところ
最小構成(5点)のうち約半数で交互性が崩れて見えることが判明した。原因は
2つあった:

1. フィットに失敗して静かに無視される候補(§3.2)が、表示には一切
   現れないまま、その側の交互の番を消費していた。生の候補選択レベルでは
   交互性を保っていても、失敗した候補が表示から消えるせいで見た目上は
   同じ側が連続しているように見えていた。→ 失敗した候補はその側の番を
   消費しないよう修正(`turn_consumed`、§3.2参照)。
2. 修正1だけでは残存(23〜45%)。フィット自体には成功しても、プール
   全体を新しい直線で絞り込み直す際に、既に交互に表示されていた途中の
   点が新しい直線の許容誤差から外れて脱落することがあり、これも表示上の
   交互性を崩していた。→ 組み合わせの採用条件に、三角保ち合いv2と同じ
   `_reg_flat_alternates`によるマージ後交互性チェックを追加(最小構成が
   揃うまでの間[`check_alternation`]のみ、§3.2参照)。

この2件の修正後、実データで最小構成(5点)の交互性違反は0件になった
(confirmed_lower 677件、confirmed_upper 161件 - 交互性を厳密に守る分
Confirmed件数はさらに絞り込まれた)。

## 1. 構成点と最小構成

下値支持線・上値抵抗線それぞれ、点1・2点目はそのまま結んだ直線、3点目
以降は`_wedge_pool_refit_side`による複数組み合わせ探索(§3.2参照)。
点1は下値側・上値側どちらからでも探索を始め(2方向、結果をマージする)、
**最小構成が揃うまでは山谷交互を強制する**(三角保ち合いv2と同じ考え方)。

厳密な交互のもとでは起点側が常に1ターン先行するため、起点側がちょうど
3点目(回帰直線確定)に達した時点で、相手側はちょうど2点(直線)になって
いる。これが**最小構成=5点(3点+2点)**の理由で、三角保ち合いのような
5点/6点の非対称は無い(どちらの側から始めても常に5点)。

最小構成が揃った後(`have_min`)は両側とも自由に探索する(交互の強制は
無くなる)。もう片方の側がまだ2点のままでも、後から3点目のピボットが
出現すれば、その時点で回帰直線に固定される(Candidate/Confirmedの前後を
問わない)。

## 2. 高さ(許容誤差・ブレイク余白の基準)

```
lo_line_at(bar):
  0点: 未定義(実際には呼ばれない)
  1点: その1点の生の価格をそのまま使う
  2点以上: 直線(2点ならその2点を結ぶ直線、3点以上なら現在の回帰直線)の値
up_line_at(bar): 同じ考え方
height_at(bar) = |up_line_at(bar) − lo_line_at(bar)|
```

回帰直線を判定する際も、この`height_at`を使って許容誤差
(`level_tolerance_mult`)を判定する - もう片方の側がまだ1点しか無い段階
でも、その1点の生の価格を暫定的な基準として使えるようにするため。

## 3. 新しい候補が出るたびの判定

### 3.1 1点目 → 2点目

そのまま結んで直線にする。傾きが正(上昇)でなければ、その探索
(この点1からの試行全体)は不成立(この時点では組み合わせが1通りしか
無いため引き直しの余地が無い)。加えて、この段階で初めて「この側の
直線」が生まれるため、相手側が既に1点以上あれば交差チェック、既に
2点以上(=傾きが定義されている)あれば収束チェックも行う(§3.2と同じ
内容、詳細はそちら参照)。いずれかを満たさなければ同様に不成立とする。
この時点では最小構成(`min_met`)は必ず未成立のため、不成立時は無条件で
Invalidated相当として探索を打ち切る(ブレイク方向のチェックは不要)。

### 3.2 3点目以降(複数組み合わせ探索)

三角保ち合いv2の回帰側と同じ考え方: この側の候補としてこれまでに採用
された点をすべて時刻順にプールとして保持し(取り消しなし)、起点
(プールの最初の点)を固定したまま、既存プールの中間点+新しい候補、と
いう組み合わせを**古い方から順に**試し、以下をすべて満たす最初の
組み合わせを新しい直線として採用する:

- 傾きが正(上昇)
- 起点・中間点・新候補それぞれが、`height_at`基準の許容誤差以内(§2)
- 急さ(ATR倍率、`min_slope_rise_atr_mult`/`max_slope_rise_atr_mult`)
- **遡及破綻チェック**: 起点〜今回の候補までの区間を生の高値/安値で
  この直線に照らしてチェック(三角保ち合いv2§5.4と同じ考え方)
- **交差チェック**: この新しい直線でプール全体を許容誤差フィルタし
  直した構成点、および相手側の現在の構成点、そのどちらのバーで
  評価しても、下値直線の値が上値直線の値未満であること(上値側は逆)
- **収束チェック**: 相手側が既に傾きを持つ(2点以上)場合、下値直線の
  傾きが上値直線の傾きより大きい(急である)こと

最小構成が揃うまで(`have_min`成立前)は、組み合わせの採用条件にもう
1つ加わる:

- **交互性チェック**: この新しい直線でプール全体を絞り込み直した
  この側の構成点と、相手側の現在の構成点を時刻順にマージした結果が
  山谷交互になっていること(三角保ち合いv2の`_reg_flat_alternates`と
  同じ関数を流用)。フィット自体には成功しても、絞り込みで途中の点が
  脱落すると表示上の交互性が崩れることがあるため(2026-08-19発見、
  §0参照)。最小構成成立後(`have_min`成立後)はこのチェックを行わない
  (§4の通り、成立後は交互性を要求しない仕様のため)。

いずれかの候補も条件を満たさなかった場合:

- 既にこの側の直線が一度でも成立していた場合、**今の(引き直し前の)
  直線より破綻方向に外れている場合だけ**、§5のブレイク判定と同じ扱いに
  する(2026-08-19、段階固定方式時代からの向き付きチェックを踏襲 - 単に
  組み合わせが見つからなかっただけで、切り上がりが強すぎるだけの候補
  まで誤ってブレイク扱いにしないため)。
- まだ一度もこの側の直線が成立していない場合は、罰則なしで探索を続ける
  (将来の候補で成立するかもしれないため)。

**いずれの場合も、最小構成が揃うまで(`have_min`成立前)は、この側の
交互の番を消費しない**(`turn_consumed=False`、2026-08-19追加)。つまり
次の候補も同じ側から探し直す(相手側には渡さない)。失敗した候補が表示
には一切現れないまま相手側に番を渡してしまうと、表示上は同じ側が連続
しているように見えてしまうため(§0参照)。

満たす組み合わせが見つかった場合は、その直線を採用し、プール全体を
新しい直線の許容誤差でフィルタし直したものを、この側の表示用構成点
(本数カウント対象)として置き換える。この場合は通常通り交互の番を
消費する。

**バグ修正の経緯(段階固定方式時代)**: 当初は直線の確定に失敗した理由
(傾き・許容誤差・急さ・遡及破綻のどれか)を問わず無条件でブレイク扱いに
していた。このため、例えば下値側の候補が実際には直線より**上**に外れて
いる(切り上がりが強すぎて急さ上限に引っかかっただけ等)場合でも
`confirmed_lower`が成立してしまい、逆方向(上値抵抗線ブレイク狙いの
ロング等)のエントリーが実際のブレイクなしで発生する不具合があった
(ユーザー報告「上値抵抗線を上抜けてないのにロングしている」)。上記の
向き付きチェックはこのバグ修正がそのまま複数組み合わせ探索方式にも
引き継がれている。

## 4. 交互性

§1の通り、最小構成(5点)は交互探索によって自動的に山谷交互になる
- ただし単に生の候補選択を交互にするだけでは不十分で、§3.2の
「番を消費しない」処理と「交互性チェック」の両方があって初めて
**表示される構成点**も交互になることが実データ検証で確認できた
(§0参照)。最小構成後の自由探索フェーズで追加される構成点(両側とも)は
交互性の対象外(三角保ち合いv2と同じ「最小構成を超えた分は交互を
強制しない」方針)。

## 5. ブレイク・逸脱判定

両側とも直線(2点または3点以上)が揃った(`have_min`)後、毎バー生の
高値・安値をチェックする:

```
lo_val(j) = lo_line_at(j)
up_val(j) = up_line_at(j)
height(j) = |up_val(j) − lo_val(j)|
buf(j) = height(j) × breakout_buffer_mult

下値支持線ブレイク: 安値[j] < lo_val(j) − buf(j)
上値抵抗線ブレイク: 高値[j] > up_val(j) + buf(j)
```

同じバーで両方トリガーする場合は下値支持線ブレイクを優先(教科書通りの
上昇ウェッジの想定方向)。`breakout_type`が`close`なら終値でも同方向に
確定しているか確認する。

- 最小構成が揃っている(`min_met`)状態でブレイクが成立 →
  `confirmed_lower`または`confirmed_upper`。
- 最小構成が揃う前にブレイクが成立 → `Invalidated`。

### 5.1 収束チェック(任意、既定オフ)

起点(点1)での値幅と、ブレイクしたバーの値幅を比較し、
`max_breakout_height_ratio`(既定0=無効)を超えて収束していなければ
Confirmedを不採用にする。

## 6. 直線の交差チェック・収束チェック(2026-08-19、毎回検証する形に変更)

下値支持線・上値抵抗線はそれぞれ独立に決まるため、両側を何度も引き
直せる設計では、引き直しのたびに2本の直線が交差したり、収束しなく
なる(下値より上値の方が急、または平行)可能性がある。これは第1版
(常に引き直し可能・両側独立)で見つかった問題そのものであり、段階
固定方式(第2版)ではこの問題を「1回だけ固定する」ことで回避していたが、
複数組み合わせ探索方式(第3版・現行)では引き直しそのものを許容する
ため、代わりに**引き直しが起きるたびに`_wedge_pool_refit_side`内で
交差チェック・収束チェックをやり直す**ことで防止する(§3.1・§3.2参照。
ユーザー確認済み、2026-08-19)。

最小構成が確定する瞬間(`_shape_state_core_wedge_v2`本体側)にも、念の
ため同じ内容の最終防衛チェックを残している(「今まさに固定された側」と
「まだ2点結びのままの側」を組み合わせて初めて全構成点が並ぶ瞬間のため)。

実データ(USDJPY 15分足)で検証したところ、この方式で交差違反・収束
違反はいずれも0件(confirmed_lower 677件、confirmed_upper 161件、
§3.2の交互性チェック追加後の件数)。

**上昇ウェッジX(`rising_wedge_shape_x`)には未適用**: `rising_wedge_
shape`(上昇ウェッジST)を2026-08-19に複製・保存した別家系
(`_shape_state_core_wedge_x_v2`)。複製した時点(段階固定方式・§6交差
チェックのみ)のまま凍結しており、その後の§6.1急さチェック追加・
向き付きバグ修正・本章の複数組み合わせ探索方式への変更・§3.2の番の
消費抑制/交互性チェックの追加は、いずれも反映していない。ST/Xは独立に
変更しうる。

## 7. パラメータ

三角保ち合いv2からの変更点のみ記す(それ以外は同じ意味・同じ既定値):

| パラメータ | 既定値 | 意味 |
|---|---|---|
| `state` | `confirmed_lower` | 状態(candidate/confirmed_lower/confirmed_upper/invalidated) |
| `level_tolerance_mult` | 0.15 | 下値支持線・上値抵抗線どちらの許容誤差にも使う(共通) |
| `min_slope_rise_atr_mult` | 1.0 | 両直線共通の急さ下限(ATR倍率) |
| `max_slope_rise_atr_mult` | 0.0(無制限) | 両直線共通の急さ上限(ATR倍率) |
| `max_breakout_height_ratio` | 0.0(無効) | §5.1の収束チェックの比率上限 |

`bullish`相当のパラメータは持たない(上昇ウェッジ専用、下降ウェッジ
[`falling_wedge_shape`]は今回のリライト対象外で旧実装のまま)。

三角保ち合いv2と同じ(formed_barアンカー方式、point1..pointN汎用形式)。
`kind`は常に`"top"`(旧実装を踏襲)。

## 9. 既知の限界

1. `start_is_low`相当の探索方向は下値・上値どちらの1点目からでも探索する
   (2方向、三角保ち合いv2と同じ)。
2. 孤立度チェック(`pivot_spike_*`)は三角保ち合いv2から引き継いでいる。
3. 交差・収束チェックはプール全体を新しい直線でフィルタし直した後の
   構成点+相手側の現在の構成点、それぞれのバーで評価する(直線同士は
   線形なので、この評価点集合の最小バー・最大バーで交差していなければ
   その間でも交差しないことが保証される)。ただし相手側がその後さらに
   引き直された場合、その引き直し自体が(相手側の視点で)同じチェックを
   やり直すため、最終的な組み合わせは常に交差・収束条件を満たす。

## 10. 検証手順

1. 合成データで下値支持線ブレイク・上値抵抗線ブレイクそれぞれが正しく
   `confirmed_lower`/`confirmed_upper`になることを確認
   (`tests/test_chart_patterns.py`)。
2. 実データ(USDJPY 15分足)で交互性(最小構成5点の表示レベルでの交互性
   含む)・許容誤差・両直線の傾きが正・直線の交差(§6)、いずれも違反
   0件であることを確認(confirmed_lower 677件、confirmed_upper 161件、
   2026-08-19時点)。
